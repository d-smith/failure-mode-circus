## 2026-07-29 — Task 9: terraform/modules/iam-task-roles

Wrote the shared iam-task-roles module, covering both halves of the plan's
design decision (line 59):

- Shared execution role: aws_iam_role.execution created only when
  var.create_execution_role = true (default true), trust policy scoped to
  ecs-tasks.amazonaws.com, AmazonECSTaskExecutionRolePolicy attached. Meant to
  be instantiated once, in the hub, and referenced by scenarios rather than
  recreated per-scenario — the boolean toggle exists so a scenario root
  module can call this same module for just its task role without a second
  execution role being created.
- Per-scenario task role factory: aws_iam_role.task for_each over
  var.task_roles (map keyed by logical scenario name, e.g.
  "reference-service"), each with the same ecs-tasks.amazonaws.com trust
  policy plus whatever managed_policy_arns that scenario lists (empty by
  default, matching "reference service needs ~none"). Attachments are built
  via a flattened map (merge(...) over a list of per-role maps) so a scenario
  needing e.g. SQS access later just adds an ARN to its task_roles entry.

outputs.tf exposes execution_role_arn/name (null when
create_execution_role = false) and task_role_arns/names maps.

## 2026-07-29 — Task 10: terraform/modules/github-oidc-role

Wrote the github-oidc-role module as a one-role-per-instantiation factory
(hub will call it twice in task 15: once for terraform-apply, once for
build-and-push/deploy). Deliberately does NOT hardcode any permissions
itself — var.policy_arns (managed policy ARNs) and var.inline_policy_json
(a caller-supplied aws_iam_policy_document JSON string) are how each purpose
gets its own scoped permission set, matching the plan's requirement that
terraform-apply be broad and build-and-push/deploy be narrow (ECR push + ECS
RegisterTaskDefinition/UpdateService only).

Trust policy: sts:AssumeRoleWithWebIdentity from the Federated OIDC provider
(var.oidc_provider_arn, sourced from bootstrap's github_oidc_provider_arn
output), conditioned on aud = sts.amazonaws.com and sub matching
repo:<github_repo>:ref:refs/heads/<github_branch> (StringLike, so a caller
can pass a wildcard branch pattern if ever needed) plus, if
allow_pull_requests = true, also repo:<github_repo>:pull_request — for
plan-only roles that PR-triggered workflows need to assume regardless of
branch.

Removed the now-redundant terraform/modules/github-oidc-role/.gitkeep.

Wrote the ecr-repo module: one aws_ecr_repository per instantiation (hub will
for_each this over "reference-service" and "k6-runner" in task 15), named
"<name_prefix>/<repo_name>". image_tag_mutability defaults to MUTABLE
(pragmatic for an early-stage project likely re-pushing tags like "latest"

jsonencode from max_image_count (default 10, keep only the last N tagged

from repeated dev pushes). lifecycle_policy_json lets a caller fully override
with raw JSON if a scenario ever needs different rules.

## 2026-07-29 — Task 12: terraform/modules/ecs-service

Wrote the generic ecs-service module, split across main.tf (task definition +
aws_ecs_service), security.tf (the service's own security group), plus the
usual variables/outputs/versions:

- var.containers is a list(object(...)) per the plan's explicit design
  decision (accept a list from day one, not a single image/port pair) —
  rendered into container_definitions JSON via a locals block, one awslogs
  logConfiguration per container pointed at var.log_group_name with
  awslogs-stream-prefix = container name.
- Service Connect is a generic passthrough surface, not opinionated about
  naming: var.service_connect_services is a list of {port_name,
  discovery_name, client_port?} that the module wires directly into the
  aws_ecs_service service_connect_configuration's dynamic "service" blocks.
  The module doesn't hardcode "reference-service.internal" anywhere — the
  reference-service scenario (task 19) will pass discovery_name =
  "reference-service" itself. enable_service_connect defaults to true even
  with an empty services list, so a task can be a Service Connect client
  without exposing anything itself.
- Task-level execution_role_arn/task_role_arn are required inputs (created
  elsewhere, by iam-task-roles) — this module doesn't create IAM roles.
- security.tf creates one SG per service: ingress on every distinct
  container port from var.vpc_cidr only (matches the project's existing
  VPC-endpoint SG pattern, no public exposure), egress all (needed to reach
  ECR/logs VPC endpoints). assign_public_ip is hardcoded false in the network
  configuration, not exposed as a variable, since public ingress was
  explicitly deferred to a future opt-in ALB module per the plan.
- extra_security_group_ids lets a caller attach additional SGs beyond the
  one this module creates, for scenarios that need to reach something more
  specific later.
